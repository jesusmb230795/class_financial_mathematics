# Reproducible Computational Finance Stack

Module: Setup and Python Ecosystem

## Lesson summary

Computational finance work is only useful when results can be reproduced by the instructor, students, and automated build systems. This note defines the technical contract for the course environment: Python version management, dependency locking, notebook execution, secrets handling, and book validation {cite}`kluyver2016jupyter,jupyterbook2025`.

The course uses `pyenv` for the local Python interpreter, `uv` for dependency resolution and virtual environment management, JupyterLab for interactive work, and Jupyter Book for the published textbook {cite}`pyenv2025,uv2025,kluyver2016jupyter,jupyterbook2025`.

## Learning objectives

By the end of this lesson, students should be able to:

- explain why reproducibility matters in quantitative financial mathematics;
- distinguish interpreter management from dependency management;
- install and synchronize the project environment with `pyenv` and `uv`;
- launch JupyterLab from the project environment;
- understand the controlled notebook execution policy used for the published book;
- handle API credentials without committing secrets;
- run the validation commands required before sharing work.

## Environment contract

| Component | Course decision | Purpose |
| --- | --- | --- |
| Python | Python 3.12 or newer, pinned locally with `.python-version` | Keeps the interpreter consistent across machines |
| Dependencies | `pyproject.toml` plus `uv.lock` | Locks the scientific Python stack deterministically |
| Virtual environment | `.venv/`, created by `uv sync` | Isolates course packages from system Python |
| Interactive work | `uv run jupyter lab` | Ensures notebooks use the project environment |
| Book build | `make book` | Generates the static HTML textbook with reviewed notebook outputs |
| Execution policy | `execute_notebooks: "cache"` with explicit exclusions | Renders outputs for reproducible notebooks without rewriting source files |
| Secrets | local `.env` or exported shell variables | Keeps API keys out of Git history |

## Local workflow

The base setup is:

```bash
pyenv install 3.12.12
pyenv local 3.12.12
uv sync
```

Launch notebooks from the project environment:

```bash
uv run jupyter lab
```

Build the book:

```bash
make book
```

Run a minimal environment check:

```bash
uv run python --version
uv run python -c "import pandas, numpy, scipy, statsmodels, sklearn, plotly, ipywidgets; print('environment ok')"
```

## Notebook execution policy

The publication build executes reproducible notebooks and caches their outputs:

```yaml
execute:
  execute_notebooks: "cache"
  cache: _build/.jupyter_cache
  timeout: 120
```

This policy lives in `_config.outputs.yml`, which is the config used by `make book`. It makes the published HTML more useful because tables, figures, and diagnostic summaries are rendered during the build. The source notebooks remain clean because generated outputs are written to `_build/html/` and `_build/.jupyter_cache/`, not committed back into `notebooks/class/`.

The `make book` target sets `RUN_INTERACTIVE_WIDGETS=0`. Dashboard notebooks should therefore render a static default chart during publication and reserve live `ipywidgets` controls for JupyterLab sessions.

Some legacy notebooks still depend on external data providers such as Yahoo Finance, FRED, Banxico, or local API-key modules. Those files are explicitly excluded from build-time execution until they are converted to deterministic classroom datasets or a controlled publication environment with credentials and cache policy is available.

For teaching, students should still run notebooks interactively in JupyterLab when the lesson requires live data, widgets, or local credentials.

## Interactive outputs

Interactive charts should be designed with two environments in mind:

- In JupyterLab, `ipywidgets` and Plotly can provide sliders, linked controls, and exploratory dashboards {cite}`plotly2015collaborative`.
- In the static Jupyter Book, interactive output must be verified after build. If an output is fragile, include a static fallback figure or a clear instruction to run the notebook in JupyterLab.

For Plotly-heavy notebooks that need to render in the static book, publish an explicit HTML output:

```python
from IPython.display import HTML, display

display(HTML(fig.to_html(include_plotlyjs="cdn", full_html=False)))
```

This preserves interactive Plotly behavior in the generated HTML while avoiding unsupported Plotly MIME warnings during the Jupyter Book build.

## Notebook version-control hygiene

Notebook files can create noisy Git diffs because they contain execution counts, metadata, and outputs. The course should keep source changes reviewable:

- avoid committing API keys, credentials, or printed secrets;
- clear large outputs before committing notebooks; the book build regenerates reviewed outputs into `_build/`;
- move reusable code into `src/`;
- keep generated HTML under `_build/`, which is ignored by Git;
- prefer MyST Markdown notes when a lesson is mostly narrative plus small code examples.

The local pre-commit hooks strip `.ipynb` outputs and execution counts, then validate notebook sources before commits.

## Validation checklist

Before sharing changes, run:

```bash
git diff --check
make book
```

For environment-sensitive changes, also run:

```bash
uv run python --version
uv run python -c "import pandas, numpy, scipy, statsmodels, sklearn; print('core imports ok')"
```
